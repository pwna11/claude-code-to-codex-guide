# 从 Claude Code 全面迁移到 Codex：踩完 10 个大坑后的实战复盘

> **摘要（Description）**：带着在 Claude Code 上积累的 Skills、`AGENTS.md` 和工作流直接迁到 OpenAI Codex + GPT-6 Astra，结果接连踩坑：修改范围失控、子 Agent 429 假完成、重试配置失效、旧规则反向束缚新模型。本文复盘最近一个月的真实会话历史与源码排查，总结出 10 条从 Claude Code 迁移到 GPT-6 + Codex 的核心避坑指南。

---

最近这个月，我把主力开发工具从 Claude Code 整体迁到了 Codex。一开始用 GPT-5.6 Sol，等 GPT-6 Astra 发布后又第一时间切了过去。

迁移之前，我平时也经常用 Codex 做代码审查（Code Review）和部分开发任务，再加上 GPT-6 各项 Benchmark 表现都很强，所以我原本以为：带着在 Claude Code 上攒下来的全套 Skills、规则和记忆直接搬过去，应该能无缝衔接。

结果完全出乎意料。一上手，各种诡异问题接连冒出来：
- 让改一句话，结果把整篇文档重写了；
- 子 Agent 撞上限流后，状态标着 `completed` 假装干完了活；
- 明明配了 30 次重试，遇到 `429` 还是秒退任务。

这几天我让 Codex 把最近一个月的会话历史彻底扫了一遍，并对照了 OpenAI 官方的迁移指南与 Codex 源码。如果你也打算从 Claude Code 切到 Codex + GPT-6，或者正在双持这两套工具，下面这 **10 条踩坑复盘**应该能帮你少走不少弯路。

---

## 1. GPT-6 对“最后一条指令”极其敏感，不锁死范围就会擅自扩权

有一次，我让它修改一份设计文档里的某句话。结果交回来一看，整篇文档的句式全被它改掉了。

一开始我以为是模型把“局部反馈”误当成了“全局指令”。后来翻完会话历史才发现，原因更微妙：那份文档原本在不同章节散落着一些祈使句，当我要求对某一段做“简洁清晰”的局部修订时，Astra 把这四个字理解成了**整篇文档的写作方针**，顺手把其他章节也一起改了。更要命的是，它在回复里信誓旦旦地写着“读者视角核对完成”，但实际上只改了局部字句，全文的文体一致性根本没做检查。

这个问题在 GPT-6 Astra 上尤其明显。**如果你不在指令末尾显式加上“只改这一处，其他段落一律不动”，它就会顺着你的最后一句话自行扩大执行范围。**

---

## 2. 子 Agent 失败后不会自动续跑，甚至会“假装已完成”

在多 Agent 协作场景下，子 Agent（Subagent）一旦撞上 `429` 限流，父 Agent 偶尔会发起定向重试，但大多数时候是直接跳过。

更隐蔽的坑是 **“假完成”**：
有时候子 Agent 的状态明明标着 `completed`，但点开返回内容只有冷冰冰的一句：*“我会先读取规则，再检查……”*——后面真正的审查结果一个字都没有。而父 Agent 只认状态码，看到 `completed` 就默认这一步已经顺利跑完，直接带着空结果往下走了。

所以，凡是依赖子 Agent 产出的关键步骤，不能只看状态是不是 `completed`，必须让父 Agent 校验返回结果里是否包含实质性的交付物。

---

## 3. `429` 限流时重试配置根本不生效，Codex 会直接退出任务

Agentic 会话的 Token 消耗跟普通网页聊天完全不是一个量级。尤其是我的日常工作流经常需要同时调度多个子 Agent 并行跑复杂任务，触发速率限制（Rate Limit）是家常便饭。

为了保证长程任务在我离开电脑时也能跑完，我特意把配置里的重试上限拉到了 `30` 次。结果终端里还是频繁弹出：

```text
正在重新连接 1/30，exceeded retry limit, last status: 429 Too Many Requests
```

刚连第 1 次就直接报错退出了。我去翻了 Codex 的源码才发现真相：**Codex 底层对 `429` 错误压根就不走重试循环，一旦碰到直接中止当前任务。**

针对这个问题，目前最有效的应对办法有两个：
1. **从源头压降并发与单次消耗**：限制同时启动的子 Agent 数量，避免一上来就打满并发；同时把日常任务的 `reasoning_effort` 从 `max` 降到 `high`，绝大多数编码任务完全够用。
2. **保证账号本身的配额充足**：如果你高频使用 Codex 跑多 Agent 任务，普通额度的账号很容易频繁撞上 `429` 墙导致任务半途而废。建议直接用高配额的 ChatGPT Plus / Pro 订阅（需要充值或升级订阅的朋友可以通过 [GetGPTPlus](https://getgptplus.app/) 快速自助搞定），从根源上减少限流中断。

---

## 4. 模型变强之后，旧时代的“保姆规则”反而成了负资产

在 GPT-6 之前，我们写系统提示词和 `AGENTS.md`，八成精力都在做一件事：**替模型补齐基础能力**。

比如“改完代码记得跑测试”“动手前先想清楚”“不要擅自扩大范围”，本质上都是在提醒旧模型去做它自己想不到的事。但到了 Astra 这一代，这些动作已经内化成了模型的默认行为了。

不仅不需要提醒，旧规则甚至会反噬效率：
以前为了防止旧模型乱改代码，我们习惯写死硬边界（比如“未经许可绝不修改其他文件”“每一步修改前先停下来确认”）。GPT-5.6 Sol 还会灵活变通，一口气把活干完；但 **Astra 会死抠字眼当真**——它本来就比 Sol 更倾向于写完初步实现就停下来等你审查，一旦看到这类旧规则，就会变成“改两行停一下”的复读机。

模型升级后，提示词的职责已经变了：**从“教它怎么干活（补能力）”变成了“划定安全边界与验收标准”**。现在最该做的不是往配置里加规则，而是删规则。

---

## 5. Skill 描述写得越宽泛，模型越容易加载错误上下文

当你积累的 Skills 越来越多时，Codex 会为了节省上下文空间而自动压缩 Skill 描述。这时候，描述写得越宽泛，模型看到的有效区分信息就越少，越容易挂错 Skill。

OpenAI 官方文档里专门点名了一个典型反模式：
- **太宽泛的写法**：`Use when working with databases, queries, models, or persistence`（只要任务沾一点数据库的边就会被误触发）
- **精准的写法**：`Use when adding or changing a migration, or reviewing its rollout`（只在新增/修改数据库迁移或审查发布时才加载）

写 Skill 的 `description` 时，不要写它“属于什么领域”，要写它**“在什么具体动作下才触发”**。

---

## 6. `AGENTS.md` 应该做“按需路由器”，而不是“全量百科全书”

很多人习惯在 `AGENTS.md` 开头写上：*“每次修改代码前，必须先完整阅读 `architecture.md`、`database.md` 和 `deployment.md`。”*

这种写法在多轮任务里就是在白白烧上下文。更糟的是，跟当前任务无关的指导塞得越多，模型的注意力就越容易被带偏。

正确的做法是把 `AGENTS.md` 改造成**按需路由表（Router）**：
- 修改数据表结构（Schema）时 $\rightarrow$ 才去读 `database.md`
- 准备构建与发版时 $\rightarrow$ 才去读 `deployment.md`

同理，以前很多 Skill 写得像事无巨细的菜谱，第一步干嘛、第二步干嘛全部锁死。GPT-6 Astra 对模糊意图和代码上下文的理解力强得多，写得太死反而把它的手脚捆住了。

---

## 7. Astra 天生偏保守，需要对“安全工作流”做显式白名单授权

用过 GPT-5.6 Sol 的人都知道，给它一个任务它能闷头干很久。但 GPT-6 Astra 性格大变：哪怕后面还有活没干完，它也喜欢在完成初步实现后立刻停下来交给你审查。

如果你希望它一鼓作气做完，有两个办法：
1. **派活时写清“完成（Done）”的定义**：在 Prompt 里直接写明“改完代码后自己跑测试、检查报错并修好，直到测试通过再交付”。
2. **在 `AGENTS.md` 里给安全操作开绿灯**：对于完全在本地运行、没有生产风险的操作，直接写入全局授权。比如 OpenAI 官方推荐的这段话就非常好用：

```markdown
The local tests use disposable fixtures and have no production access. Run them, fix failures caused by the requested change, and rerun affected tests without asking for approval at each step.
```

加上这句之后，模型就不会每跑一次本地单测都停下来找你点确认了。

---

## 8. 文档写得“AI 味重”，不是措辞问题，而是没给好样本

让 GPT-6 写技术文档时，很多人觉得它写出来的东西一股“AI 味”。

原因在于，GPT-6 默认把**“解释完整、结构对称、面面俱到”**当成好文章的标准；而我们实际需要的，往往是**“单刀直入讲清一个核心判断，让读者立刻明白为什么重要”**。

如果在 `AGENTS.md` 里只加一句笼统的 `不要有 AI 味`，基本没用，因为模型根本不知道你眼里的“AI 味”长什么样。真正管用的做法是：
1. **给一段你认可的真实样稿（Few-shot）**，让它先对齐语气和节奏；
2. **写长文前先试写一小段**，看一眼调性对了，再让它展开写全文，避免整篇写完推倒重来；
3. **把“核心观点对不对”和“文字顺不顺”拆成两步检查**，千万不要用漂亮的文笔润色去掩盖主题本身的跑偏。

---

## 9. 别自己人工逐行改配置，让 Astra 替你做一次规则审计

当你的 `AGENTS.md` 和 Skills 攒了成百上千行之后，哪些规则已经过时、哪些互相打架、哪些触发范围太宽，靠肉眼一条条排查非常痛苦。

最省事的办法，是直接让 GPT-6 Astra 对你的配置目录做一次**只读审计（Read-only Audit）**。你可以直接用下面这段思路让它帮你体检：

- 检查是否存在**前后矛盾**的指令；
- 找出触发范围过宽、容易误加载的 **Skill 描述**；
- 揪出所有要求**无条件全量加载**长文档的规则；
- 找出写死的**多轮繁琐审查流程**；
- 找出把**一次性临时环境 Bug** 当成永久铁律写进全局配置的历史遗留项。

然后让它按照 **`[保留]`、`[收窄范围]`、`[移入专用 Skill]`、`[改为脚本/Linter 检查]`、`[待验证后删除]`** 五个档位输出清理建议。

> **注意底线**：千万不要因为新模型变聪明了，就顺手把权限边界、生产环境隔离、敏感操作确认等**安全类约束**也删掉——安全底线任何时候都得留着。

---

## 10. 警惕跨模型水土不服：Claude Code 的好规则，可能是 GPT-6 的紧箍咒

如果你平时在 Claude Code 和 Codex 之间来回切换，或者同一套 `~/.codex/skills` / 项目规则会被不同模型调用，这一点一定要留神。

我这次迁移踩的最大暗坑就在这：**专门针对 Claude (Sonnet / Opus) 脾气调教出来的 Skills，原封不动喂给 GPT-6 Astra，往往会造成严重的过度约束，导致输出质量断崖式下跌。**

如果某条规则是为了治某个特定模型的毛病而写的，建议：
- 在规则里明确标注它的适用模型；
- 或者拆成按模型条件加载的配置，只在调用对应模型时生效。

**永远不要假设同一套 Prompt 和 Skill 在不同家族的大模型上会有相同的行为表现。**
